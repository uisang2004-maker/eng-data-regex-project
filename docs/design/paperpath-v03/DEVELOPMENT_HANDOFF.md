# PaperPath 개발 인계서

> **디자인 확정본:** v03  
> **기획 기준일:** 2026-11-04 (4차 개정)  
> **대상 구현:** Streamlit 기반 학부생용 영어 논문 독해 보조 도구  
> **문서 목적:** 개발 AI/개발자가 시각적 기준과 실제 기능 요구사항을 혼동하지 않고 구현하도록 전달

## 0. 반드시 지킬 기준

### 0.1 디자인과 기능의 기준 파일

| 구분 | 기준 | 사용 방법 |
|---|---|---|
| 시각 디자인 | `references/paperpath-v03-approved.png` | 최종 화면의 레이아웃, 색, 위계, 간격, 분위기 기준 |
| HTML/CSS 참고 | `references/index-v03-visual-reference.html` | 스타일 토큰과 화면 마크업 참고. 그대로 제품 코드라고 간주하지 말 것 |
| 기능 요구사항 | `references/PLAN-4th-revision-2026-11-04.md` | 기능 범위, 규칙, 데이터 정책, 기술 구조의 최우선 기준 |
| 이 인계서 | 현재 문서 | 위 세 자료를 구현 단위로 연결하고 모호한 부분을 표시 |

**충돌이 있으면 기능은 4차 기획서, 외형은 v03 캡처를 우선한다.** v03는 CSS 중심의 정적 목업이므로 실제 데이터나 상호작용의 구현 증거가 아니다.

### 0.2 제품 정체성

PaperPath는 AI가 논문을 대신 요약하거나 해설하는 서비스가 아니다. 정규식 기반 규칙이 원문에서 먼저 읽을 문장과 독해 신호를 표시하고, 사용자가 판단할 수 있도록 그 근거를 공개하는 도구다.

- 한 줄 가치: **읽는 길은 정규식이, 판단은 학생이.**
- 대상: 영어 논문을 처음 읽는 학부생
- 중심 경험: 원문 입력 → 문제·방법·결과 3줄 뼈대 → 원문 독해 신호와 근거 확인 → 필요할 때 번역
- 모든 핵심 표시의 근거는 준비된 규칙이어야 한다. 생성형 AI가 임의로 문장·정의를 만들어 표시하지 않는다.

## 1. 화면 구조

### 1.1 기본 화면

기본 진입 화면은 v03의 `논문 읽기` 탭이다. 데스크톱 기준 캡처 크기는 **1440×900**이며, 기존의 밝고 절제된 SaaS 작업 공간을 유지한다.

화면 순서는 아래와 같이 고정한다.

1. **상단 바** — PaperPath 브랜드, `논문 읽기` / `규칙 탐색` / `검증 결과` 내비게이션, 규칙 엔진 상태
2. **페이지 소개** — 제목 `논문을 읽는 길을 먼저 보여드려요.`, 짧은 설명, 실제 논문이 아닌 예시 데이터일 때의 고지
3. **입력 패널** — `arXiv ID` / `텍스트 붙여 넣기` 모드, 입력 필드, `초록 불러오기` 또는 분석 실행 버튼, 개인정보·DeepL 전송 안내
4. **먼저 읽을 3줄 뼈대** — 문제(Problem) / 방법(Method) / 결과(Result) 카드. 각 카드에 원문 문장, 탐지한 신호 문구, 한국어 이유 표시
5. **원문과 번역을 나란히 읽기** — 왼쪽 영어 원문, 오른쪽 한국어 번역. 원문의 약어·추측·확신·참조 표시와 문장 번호를 유지
6. **하단 근거 영역** — 탐지된 약어와 규칙 근거로 이동하는 진입점

현재 v03는 한 화면에서 위 순서를 보여 주는 예시 상태다. 실제 콘텐츠가 길어지면 페이지 세로 스크롤을 허용한다. 1440×900 프레임에 맞추려고 글자를 지나치게 축소하거나 본문을 잘라내지 않는다.

### 1.2 상단 탭

| 탭 | 목적 | 필수 내용 |
|---|---|---|
| 논문 읽기 | 실제 사용의 기본 작업 공간 | 입력, 3줄 뼈대, 원문 하이라이트, 번역, 핵심 근거 진입 |
| 규칙 탐색 | 탐지 로직을 투명하게 보여 주는 화면 | 준비된 규칙 목록, 규칙 설명, 긍정/제외 예시, 읽기 전용 처리 단계, 규칙별 시연 on/off |
| 검증 결과 | 정확도·한계·실험을 투명하게 보여 주는 화면 | 표본/측정 방법, 정밀도·재현율 등 실제 측정 결과, 마스킹 30편 실측 결과와 한계 |

목업에서는 첫 번째 탭만 시각적으로 완성되어 있다. 나머지 두 탭은 새 디자인 언어를 만들지 말고 같은 컴포넌트·타이포그래피·표면 규칙을 이어받는다.

### 1.3 반응형 동작

- 데스크톱(기준 1440px): v03처럼 3개 뼈대 카드를 가로 배치하고, 원문/번역을 좌우 2열로 배치한다.
- 태블릿/좁은 데스크톱: 입력 컨트롤이 겹치지 않도록 줄바꿈을 허용하고, 필요하면 원문/번역 열의 폭을 조정한다.
- 모바일: 3줄 카드는 세로 스택, 원문·번역도 세로 스택, 하단 근거 카드는 세로 스택. 가로 스크롤을 기본 해결책으로 쓰지 않는다.
- 작은 화면에서도 원문과 번역의 문장 번호·1:1 대응이 유지되어야 한다.

반응형의 세부 breakpoint는 개발 단계에서 정하되, 위 정보 순서와 접근성을 바꾸면 안 된다.

## 2. 확정된 시각 디자인 시스템

### 2.1 전체 톤

- 밝은 학술용 작업 공간 + 세련된 SaaS 제품 UI
- Linear/Notion 계열에서 영감을 얻은 절제된 밀도와 미세한 표면 구분. 특정 제품의 화면·로고를 복제하지 않는다.
- 장식보다 읽기 위계가 우선이다. 그라데이션과 그림자는 약하게 사용한다.
- 원문·결과·규칙 영역은 흰색 표면, 전체 캔버스는 매우 옅은 쿨 그레이/블루 계열

### 2.2 색상 토큰

### 2.3 모양·타이포그래피·간격

- 기본 카드 radius: **14px**. 핵심 reader card는 16px까지 허용.
- 테두리는 1px, 낮은 대비. 그림자는 `0 4px 18px rgba(26, 54, 83, .045)` 수준의 낮은 강도.
- 폰트 우선순위: `Pretendard`, `Malgun Gothic`, `Segoe UI`, `sans-serif`.
- 제목은 진한 navy/ink, 본문은 muted보다 높은 대비로 유지한다.
- 간격은 4px 단위를 기본으로 하고, 주요 간격은 8/12/16/24px를 사용한다.
- 강조 색은 의미를 구분하기 위한 것이다. 색만으로 기능/상태를 전달하지 말고 라벨·텍스트·아이콘을 함께 제공한다.
- 주요 버튼과 입력은 키보드 포커스를 명확히 표시한다. 실제 터치 컨트롤은 가능한 한 44×44px 이상의 조작 영역을 확보한다.

## 3. 기능 명세 — P0 6개

**P0 6개를 우선 완성하고 테스트한다. P1은 P0가 연결되고 테스트를 통과하기 전까지 개발하지 않는다.**

### P0-1. 입력 및 최소 전처리

**입력 모드**
- 기본 모드: arXiv ID 입력 후 공식 API로 초록 불러오기
- 보조 모드: 영어 초록/텍스트 붙여 넣기
- 두 모드는 세그먼트 컨트롤 또는 같은 디자인의 탭으로 전환
- 텍스트 붙여 넣기일 때는 적절한 높이의 textarea로 전환

**붙여 넣기 최소 방어선**
- 한 줄 개행을 공백으로 정리
- 연속 공백 제거
- 줄 끝 하이픈으로 분리된 단어 복원
- 숫자만 있는 쪽번호 줄 제거
- 동일한 짧은 머리말이 3회 이상 반복되면 제거

**요구 동작**
- arXiv ID 형식 검증과 API 실패 안내
- arXiv API 호출은 3초에 1회 이하로 제한
- 저자 필드는 수집하지 않는다.
- 사용자가 붙여 넣은 원문은 앱에서 저장하지 않는다.
- PDF 파일 업로드나 PDF 2단 편집 복원 기능을 추가하지 않는다.

### P0-2. 원문 3줄 뼈대

**세 카드의 구성**
- 문제(Problem)
- 방법(Method)
- 결과(Result)

각 카드에는 `원문 문장 + 잡힌 신호 문구 강조 + 한국어 이유 한 줄 + 탐지 근거 라벨`이 들어간다. 원문을 요약문으로 바꾸거나 생성하지 않는다.

**선택 규칙**
- 신호 문구가 있으면 해당 문장을 선택하고, 신호 문구를 굵게 강조한다.
- 문제 신호가 없을 때: 첫 문장을 `도입 문장 (배경·문제 추정)`으로 표시한다.
- 결과 신호가 없을 때: 코드·URL·공개 문장과 미래 연구·윤리 문장을 제외한 뒤쪽 후보 중 수치 또는 결과 동사가 있는 문장을 우선하여 `마무리 문장 (결과 추정)`으로 표시한다.
- 미래 연구·윤리·한계 문장은 버리지 않고 별도의 한계 후보로 보낸다.
- 방법 신호가 없을 때 임의의 문장을 만들지 않는다. 현재 기획서에 방법의 위치 대체 라벨이 정의되어 있지 않으므로, 빈 카드를 만들지 말고 `방법 문장을 찾지 못함` 상태를 표시한다. 이 상태에서 자동으로 다른 문장을 방법으로 가장하지 않는다.
- 코드·데이터 공개 문장 및 URL은 3줄 뼈대 대체 문장으로 채택하지 않는다.

**이유 문구**
- 패턴 파일의 설명을 사용한다.
- 예시: `results show → 결과를 알리는 표현`, `we introduce → 새로운 방법을 제안하는 신호`.
- 규칙 근거가 없으면 근거가 있다고 꾸미지 않는다.

### P0-3. 약어 → 풀네임

- 정규식은 괄호 안 약어 후보를 찾는다.
- Python 함수가 약어 글자와 앞 단어 첫 글자를 순서대로 맞춘다.
- 대문자 중심 맞추기에 실패하면 전체 글자로 한 번 재시도한다.
- 동적 정규식 생성 방식은 사용하지 않는다.
- 툴팁/포커스 설명에서 약어와 풀네임을 보여 준다.
- 정의를 찾지 못하면 `정의를 찾지 못함`을 명시한다.
- `GRU`, `YOLO`, `LoRA`, `RAG`, `BERT` 및 전체 글자 재시도 사례 `CoT`를 테스트한다. `BiLSTM`, `XGBoost`, `k-NN` 등 실패 사례는 잘못된 정의를 지어내지 않는다.

### P0-4. 추측·가능성 및 확신·참조 표시

- 추측·가능성은 3등급으로 나누지 않고 **단일 등급**으로 표시한다.
- 기본 동사/부사 신호: `may`, `might`, `could`, `suggest(s)`, `indicate(s)`, `likely`, `possibly`, `perhaps`, `appears to`, `seems to` 등 기획서 규칙.
- `may be applied`, `could also be easily extended`처럼 가능/허용의 의미인 문맥은 제외 목록으로 처리한다.
- 부정어·부사 최대 2개까지 끼어드는 형태를 테스트한다. 문장 전체의 의미를 완전히 이해한다고 주장하지 않는다.
- 확신 신호와 인용/참조는 별도 표시로 유지한다.
- 하이라이트의 정확도/한계는 검증 결과 화면에서 실측값과 함께 설명한다.

### P0-5. 영한 나란히 보기 및 마스킹 비교

**기본 원칙**
- 번역은 선택 기능이다. 번역을 사용하지 않아도 P0-1~P0-4, P0-6의 핵심 기능은 동작한다.
- 번역 패널은 v03처럼 원문 옆에 둔다.
- 권장 초기 화면은 번역 패널을 펼친 상태로 보여 주되, 아직 번역이 실행되지 않았다면 빈 결과 대신 `번역하기` CTA를 보여 준다. 화면 진입이나 입력 변경만으로 API를 자동 호출하지 않는다.

**호출 시점**
1. 사용자가 `번역하기` 버튼을 누를 때만 마스킹 ON 번역을 1회 실행한다.
2. `마스킹 끔과 비교` 버튼을 누를 때만 마스킹 OFF 번역을 추가 실행한다.
3. 입력 변경/Streamlit rerun마다 번역 API가 중복 호출되지 않도록 세션 상태 및 캐시를 관리한다.
4. 동일 문장 결과는 캐시하여 불필요한 재호출을 줄인다.

**문장 정렬·오류 안전장치**
- 보호 토큰에 약어·인용·수치 등을 포함하고, DeepL XML 처리(`tag_handling=xml`, `ignore_tags=x`)를 사용한다.
- 문장별 요청과 DeepL 재분리 비활성화(`split_sentences=0`)를 사용한다.
- 원문/번역 문장 개수가 맞으면 1:1로 나란히 표시한다.
- `len(en) != len(ko)`이면 문장별 1:1 정렬을 강제로 하지 말고 문단 단위 안전 화면으로 전환한다.
- 429, 456, 네트워크 오류에서 앱을 중단하지 않는다. `번역을 잠시 사용할 수 없음`을 안내하고 캐시가 있으면 캐시를 표시한다. 정규식 기능은 계속 동작한다.
- 마스킹 ON/OFF의 효과가 크다고 결과 확인 전에 단정하지 않는다. 30편 실측으로 효과를 판단한다.

**외부 전송 안내**
- 번역 버튼 실행 전에 영어 텍스트가 DeepL API로 전송됨을 사용자에게 명확하게 안내한다.
- 앱은 사용자 입력을 저장하지 않는다. DeepL 측 데이터 보관/활용 조건은 원본 기획서 기준 미확인으로 남아 있으므로, 근거 없이 `외부 저장되지 않는다`고 표시하지 않는다.
- API 키는 `.env`로만 관리하고 소스 코드/화면/로그에 노출하지 않는다.

### P0-6. 규칙 근거 및 읽기 전용 단계 보기

- 하이라이트를 누르거나 포커스하면 어떤 규칙이 왜 적용되었는지 볼 수 있어야 한다.
- `읽기 전용 단계 보기`는 전처리 → 문장 분리 → 약어 탐지 → 뼈대 선택 → 추측/확신/참조 탐지 → 선택적 번역의 순서를 보여 준다.
- 각 단계에는 입력/출력 예시와 사용 규칙의 설명을 연결한다.
- 준비된 규칙만 on/off할 수 있게 한다. on/off 시 데모 결과의 하이라이트가 바뀌어야 한다.
- 사용자가 임의의 정규식을 입력·실행하는 자유 Regex 실험실은 만들지 않는다.
- `규칙 탐색` 탭에서 같은 설명을 더 자세히 제공한다.

## 4. 번역 외의 인터랙션과 UI 상태

### 4.1 필수 상태

- 초기/대기: 입력 대기, 엔진 상태를 대기로 표시
- 불러오는 중: arXiv 요청 중임을 명시하고 중복 제출 방지
- 분석 완료: 3줄 뼈대, 하이라이트, 카운트 표시
- 입력 오류: ID 형식/빈 입력/텍스트 길이 등의 오류를 필드 근처에서 설명
- API 오류: arXiv/DeepL 호출 오류를 구분해 표시
- 규칙 부분 미탐지: 거짓 문장을 만들지 않고 `정의를 찾지 못함`, `방법 문장을 찾지 못함` 등 텍스트 상태로 표시
- 번역 미실행: 번역 패널 내부에 `번역하기` CTA 표시
- 번역 완료: 문장별 1:1 정렬 및 캐시된 결과 표시
- 비교 완료: 마스킹 ON/OFF 차이를 구분 표시
- 번역 오류: 번역만 실패하고 독해 분석은 살아 있는 상태

### 4.2 카운트와 상태 배지

v03의 `약어 1`, `추측·가능성 2`, `확신 1`, `참조 1` 칩은 고정 문구가 아니라 현재 분석 결과에서 계산한다. 결과가 0이면 0건 또는 빈 상태를 명시한다. 색과 숫자 외에 항목 이름을 항상 제공한다.

상단 `규칙 엔진 준비됨`도 실제 앱 초기화/오류 상태에 연동한다. 프로토타입처럼 무조건 준비됨으로 하드코딩하지 않는다. 상단의 `PP` 원형 표시는 로그인 프로필 기능이 아니다. 인증을 추가하지 말고 장식용 브랜드 모노그램/비상호작용 요소로 처리한다.

## 5. 기술 구조와 구현 경계

**기술 스택은 Streamlit을 유지한다.** 프론트엔드 프레임워크를 임의로 교체하지 않는다.

| 파일/모듈 | 책임 |
|---|---|
| `app.py` | Streamlit 화면, 입력, 결과 레이아웃, 사용자 액션과 세션 상태 |
| `src/patterns.py` | 준비된 정규식과 규칙 설명(잡는 것/예시/제외 사례) |
| `src/collect.py` | arXiv ID 기반 공식 API 초록 호출, 샘플 수집(요청 간격 준수) |
| `src/clean.py` | 텍스트 정리, 하이픈 복원, 인용/수식 선마스킹, 문장 분리 |
| `src/extract.py` | 약어, 3줄 뼈대, 추측/확신/참조 탐지 |
| `src/translate.py` | 보호 마스킹, DeepL 호출, 결과 개수 확인, 복원, 캐시, 오류 처리, 조사 띄어쓰기 정리 |
| `src/analyze.py` | 정밀도·재현율·뼈대 채움률·마스킹 실험 집계 |
| `tests/` | 규칙 양성/음성/경계 사례, 왕복·정렬·오류 비전파 테스트 |
| `.env` | DeepL API 키. git에 커밋하지 않음 |

**역할 경계**
- 화면은 입력/시각화/상태 표시를 담당한다. 화면 코드에 regex를 흩어 놓지 않는다.
- 규칙의 실체와 설명은 `patterns.py`에 모은다.
- 약어 후보 탐지(regex)와 글자 매칭(Python 함수)을 분리한다.
- 번역은 regex 엔진을 대체하지 않는다.
- 사용자 원문을 파일/DB에 저장하거나 로그에 전문 출력하지 않는다.

## 7. 검증 결과 탭의 표시 원칙

검증 화면은 실제 측정 결과와 목표/예정치를 구분한다.

- 규칙 정밀도: 초록 20편 검수형 평가 계획. 목표는 약어 0.9 이상, 추측·가능성 0.8 이상이며, 측정 전에는 `목표`로 표시한다.
- 규칙 재현율: 10편 소표본 점검 계획. 실제 측정 전 숫자를 만들지 않는다.
- 3줄 뼈대 채움률: 신호 문구만으로 셋 다 채운 기존 측정치 16%를 기획서에 명시된 시점/표본과 함께 설명하고, 대체 규칙 반영 후 결과는 재측정한 실제 값만 표시한다.
- 마스킹 기여: 초록 30편 실측 예정/결과. 사전 3문장 실험에서는 마스킹 OFF에서도 `BERT`, `3.1%`, `[4]`가 보존되었고 `Table 1`이 `표 1`로 변형된 사실을 숨기지 않는다.
- 소표본 결과는 일반화하지 않는다. 표본 수와 측정 방식, 한계를 같이 표기한다.

## 8. 권장 시연 흐름 (약 3분)

1. arXiv ID 입력 또는 제공된 텍스트 예시 선택
2. 초록을 불러와 최소 전처리 후 분석
3. 문제·방법·결과 3줄 뼈대가 원문 문장으로 채워지는 모습 확인
4. 신호 문구와 한국어 이유를 읽고, 추정 라벨이 붙은 카드는 추정임을 확인
5. 원문에서 RAG 툴팁, 추측 표현, 확신 표현, 참조 표시를 확인
6. `읽기 전용 단계 보기`에서 준비된 규칙 하나를 켜고/꺼서 하이라이트 차이를 확인
7. 필요할 때 번역하기를 눌러 영한 대응을 확인
8. 선택적으로 마스킹 OFF 비교 실행
9. 검증 결과 탭에서 정밀도/한계와 마스킹 실측을 설명

번역은 시연의 필수 시작 단계가 아니다. 번역을 실행하지 않아도 제품의 핵심 가치가 드러나야 한다.

## 10. 미확정/주의 사항

1. **방법 문장 미탐지 시 대체 규칙:** 현재 4차 기획서는 방법에 대해 `we/our`가 들어간 첫 문장을 선택한다고 되어 있으나, 해당 문장이 없을 때의 위치 대체 라벨은 명시하지 않는다. 따라서 임의의 문장을 방법으로 표시하지 말고 `방법 문장을 찾지 못함`으로 처리하는 것을 권장한다.
2. **번역 초기 노출:** v03는 번역이 완료된 예시 화면이다. 실제 앱은 번역 API를 자동 호출하지 않는다. 번역 패널은 열어 두되 미실행 상태에서 버튼을 제공하는 방식으로 시각 디자인과 지연 실행 요구를 함께 만족시킨다.
3. **검증 수치:** 기획서의 목표치, 과거 표본 측정치, 앞으로 할 실험을 구분한다. 아직 실행하지 않은 20편/30편 평가 결과를 채워 넣지 않는다.
4. **DeepL 데이터 취급:** 원본 기획서에서 외부 서비스의 데이터 보관·활용 여부는 미확인이다. 전송 사실을 표시하되 보관되지 않는다고 단정하지 않는다.
5. **시연 데이터:** 화면에 들어간 RAG 문장과 번역 예시는 화면 이해를 위한 예시다. 실제 논문 데이터와 혼동되지 않게 표시한다.
